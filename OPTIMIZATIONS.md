### BTCPAY-OPT-01: Return Cancelled when the biometric prompt starts after the activity state is saved

- **What**: Biometrics.showPrompt prepares the lock cipher on Dispatchers.IO, then calls BiometricPrompt.authenticate. androidx.biometric 1.1.0 ignores authenticate() and calls no callback when the FragmentManager state is saved (true from onStop). If the user leaves the app while the cipher is prepared, the coroutine never resumes and the busy flag of the caller stays set. On LockScreen, Unlock stays disabled on 'Waiting...' and BackHandler blocks back, so only a force stop releases the app. AppLockOfferDialog cannot be closed, so onboarding is stuck. OwnerCheck and the spend gate stay stuck until the user leaves the screen. While such a screen is on top, promptShowing stays true, so a trip to the background shorter than 120 s does not lock. The window is longest (up to more than 1 s) on the first prompt after install or after a new fingerprint, when the StrongBox key is generated. The trigger is rare.
- **Where**: app/src/main/java/com/btcpayapp/core/security/AppLock.kt:312-315 (Biometrics.showPrompt); ui/screens/lock/LockScreen.kt:95,162; ui/screens/onboarding/ApiKeyScreen.kt (AppLockOfferDialog); ui/screens/settings/AppSettingsScreen.kt (OwnerCheck.confirm); ui/components/SpendGate.kt:77
- **Change**: Add one line after line 313 and before `return suspendCancellableCoroutine`: `if (activity.supportFragmentManager.isStateSaved) return AuthOutcome.Cancelled`. The library tests the same condition. The check runs in the same main-thread step as authenticate(), so no race occurs. The finally block in prompt() then clears promptShowing, and each caller clears its busy flag. Do not add an ON_RESUME re-prompt: one tap on Unlock is enough.
- **Benefit**: A user who leaves the app during prompt preparation cannot come back to a lock screen that only a force stop releases, or to an onboarding dialog that does not close. Confirm buttons on Settings and Send work again. The 'Lock after' rule applies again on those screens. One line fixes all 4 prompt callers.
- **Evidence**: javap of biometric-1.1.0.aar (Gradle cache), BiometricPrompt.authenticateInternal: `mClientFragmentManager.isStateSaved()` -> Log.e("Unable to start authentication. Called after onSaveInstanceState().") -> return, with no callback. AppLock.kt:312 `withContext(Dispatchers.IO) { lockCipher() }`; its comment at :307-311 says key generation takes 'several hundred milliseconds to over a second'. Keystore.kt:113 requests StrongBox. LockScreen.kt:95 prompts from LaunchedEffect(Unit); :162 `enabled = !authenticating`. AppLock.kt:294-298 sets and clears promptShowing only around showPrompt. :112 copies it to leftDuringPrompt, which :127 reads for the 120 s rule. :197 reads it to hold the idle lock. Not reproduced on a device. No crash log.
- **Safety**: This is a change to security-review code. Biometrics.showPrompt is the app lock and spend gate prompt, and lines 312-313 come from 7d97a35 (Report: BTCPAY-SEC-002). These lines do not change. The new line goes directly after them in the same function. It fails closed: it returns Cancelled, never Success, so no lock or spend gate opens, and every Success still needs the cipher. No change to the Keystore, keys, storage, schemas or preference keys. No new dependency.
- **Verify**: The library behaviour was checked with javap, and all 4 callers were read. After the change: turn on the app lock, install fresh, open the app and press Home within 1 s while the lock screen prepares the first prompt. Come back: Unlock must be enabled and one tap must show the prompt.
- **Effort**: S. **Risk**: low. **Net lines**: about +2 (estimate).
- **Owner check**: Confirm that you accept a one-line change in the SEC-002 prompt function. It only returns Cancelled, and it makes the 120 s rule and the idle lock apply again, so the lock gets stricter.
- **Owner decision**: Owner approved the one-line change in the SEC-002 prompt function (it fails closed).
- **Verified**: `./gradlew :app:testDebugUnitTest :app:assembleDebug` passed (601 tests). javap of biometric-1.1.0 shows the same isStateSaved check. Not checked: no run-time check on a device (the Home-during-first-prompt test in Verify).
- **Status**: applied

### BTCPAY-OPT-02: Start the screen's own requests first on pull-to-refresh in Home and Wallet

- **What**: HomeViewModel.refresh and WalletViewModel.refresh wait for session.refresh() (stores, users/me, server/info), then for refreshPaymentMethods(). Only then do they start the screen's own requests. Thus a pull takes 3 round trips in sequence before the data changes. The pull indicator binds to state.refreshing, which only loadDashboard / load set. Thus the indicator hides on release, and the data changes about 2 round trips later. When the session failed at start, Home also loads the dashboard two times (one time from the store collector, one time from refresh).
- **Where**: app/src/main/java/com/btcpayapp/ui/screens/home/HomeScreen.kt:214-221 (HomeViewModel.refresh), :238-241 (loadDashboard); app/src/main/java/com/btcpayapp/ui/screens/wallet/WalletScreen.kt:390-396 (WalletViewModel.refresh); app/src/main/java/com/btcpayapp/data/session/SessionManager.kt:270-312 (refresh), :326-338 (refreshPaymentMethods); app/src/main/java/com/btcpayapp/ui/components/Screen.kt:153-154
- **Change**: Home: call loadDashboard(activeStoreId, refreshing = true) first (skip it if no store is known). Then, in one launch, call session.refresh(), read the store id again, call refreshPaymentMethods(storeId), then loadBalances(storeId). Wallet: call load(refreshing = true) first, then launch session.refresh() and refreshPaymentMethods(). The init collectors that exist (HomeScreen.kt:184-206, WalletScreen.kt:276-324) cancel the job in flight and reload if the store or the methods change.
- **Benefit**: The Home invoices, totals and unseen count, and the Wallet balance and history come back after 1 round trip, not 3. Estimate: about 2-6 s faster per pull on Tor, about 0.2-0.6 s on clearnet. The indicator stays up until the data is in. The duplicate Home dashboard load after a failed session start goes away.
- **Evidence**: HomeScreen.kt:216-220 and WalletScreen.kt:392-394: session.refresh() -> refreshPaymentMethods() -> screen load, in sequence. SessionManager.refresh holds refreshMutex and awaits three async calls. Screen.kt:154 PullToRefreshBox(isRefreshing = refreshing == true). HomeScreen.kt:241 and WalletScreen.kt:507 are the only places that set refreshing. loadDashboard uses only the store id; only loadBalances reads enabledPaymentMethodIds. Wallet load reads hasPermission() from the stored key. Http.kt:123 useCaches = false. Round-trip times are estimates, not measured.
- **Safety**: Only the order of read-only GET requests in two view models changes. git blame on HomeScreen.kt:214-221 and WalletScreen.kt:390-396 gives a8d48af and f2d14a0, not a 'Report:' commit. No storage, schema, preference key, encryption or key handling is touched. No dependency.
- **Verify**: The review checked that the collectors cancel the job in flight, so a dashboard load that starts before session.refresh cannot write data for an old store. After the change: count GETs in the server access log for one pull on Home and on Wallet, before and after.
- **Effort**: S. **Risk**: low. **Net lines**: about 0 (estimate).
- **Verified**: `./gradlew :app:testDebugUnitTest :app:assembleDebug` passed (601 tests). Not checked: no run-time check on a device and no count of GETs in a server access log (the Verify step); no unit test covers the two view models.
- **Status**: applied

With the reduced-motion fade the result is the same. Examples: Invoice details opened from Checkout also closes the customer Checkout. Scan opened from Send also closes the Send form. Refund also closes Invoice details. Store settings > Webhooks > Edit webhook lands on Store settings.
- **Where**: app/src/main/java/com/btcpayapp/ui/components/Screen.kt:108 (AppScreen navigation IconButton); app/src/main/java/com/btcpayapp/ui/nav/AppNavHost.kt:261-263 (back), :270 (backFrom)

- **Benefit**: A double or fast tap on the back arrow closes one screen, not two. The customer-facing checkout QR, a half-filled send form or an invoice detail no longer closes by accident. One line covers the 44 screen files that pass onBack to AppScreen. The system back gesture does not change.
- **Evidence**: AppNavHost.kt:262 `{ if (navController.previousBackStackEntry != null) navController.popBackStack() }`, with no top-of-stack check. grep 'onClick = onBack' gives 1 hit (Screen.kt:108). grep dropUnless in app/src/main/java gives nothing.
